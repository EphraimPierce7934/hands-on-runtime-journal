# Malformed multipart form-data API requests: speech-to-text file fields in Node.js

The constraint that changes this diagnosis is structured output correctness: an e-commerce review service cannot turn an audio upload into a useful finding if the request is rejected before transcription starts. **Short answer: treat a malformed speech-to-text request as a wire-format investigation, and verify capability, framing, and the file part in that order.** A generic 400 is only a symptom.

I start with a deliberately boring fixture: one short recording, a known extension, a declared MIME type, and a request ID captured beside the response. That gives a code-review pipeline a stable input before it has to classify findings such as `missing_file` or `invalid_audio`. Fast feedback matters more than a clever upload helper here.

## How should Node.js, Express, and Next.js speech-to-text API requests expose multipart failures?

Separate the upload into three observable layers. First, capability selection: is the target speech-to-text operation available under the current account and deployment? Second, HTTP framing: did the client send a multipart body whose boundary matches its `Content-Type`? Third, application parsing: did Express, Next.js, a proxy, or a body-size policy alter or consume the stream before the handler saw it?

This ordering prevents a parser problem from being mistaken for a model problem. It also makes a review finding actionable. “API returned 400” is weak. “The request declares `multipart/form-data` without a boundary” points to a specific change.

The first trap is manually setting the top-level content type. Native `FormData` generates a boundary and the fetch implementation serializes the matching delimiters. If code overwrites the header with only `multipart/form-data`, the receiver may have no boundary with which to split the parts. Don't manufacture the header unless the code also owns the complete multipart serialization.

The second trap is treating the file field as an implementation detail. The field name is part of the API contract. Use the exact documented name, include a filename for an in-memory buffer, and make the blob's media type agree with the bytes. An MP3 labeled `audio/wav` is a different finding from a missing boundary, even if both eventually surface as 400.

## The small experiment that distinguishes framing from parsing

Send one known-good recording through the same deployed path used by the application. Log metadata only: method, route, top-level content type, field names, filename, MIME type, byte length, response status, and any request ID. Never put the bearer token or audio bytes in the log.

In a Node.js route, the important behavior is that the request body is assembled by `FormData`, while the endpoint receives the resulting stream. The example below keeps the boundary under the fetch implementation's control and makes the file metadata explicit.

```ts
const audioBytes = new Uint8Array([1, 2, 3]);
const form = new FormData();
form.append(
  "file",
  new Blob([audioBytes], { type: "audio/mpeg" }),
  "review-note.mp3",
);

const response = await fetch(process.env.SPEECH_TO_TEXT_URL!, {
  method: "POST",
  headers: {
    Authorization: `Bearer ${process.env.SPEECH_TO_TEXT_TOKEN!}`,
    Accept: "application/json",
  },
  body: form,
});

const responseText = await response.text();
if (!response.ok) {
  throw new Error(`Transcription request failed (${response.status}): ${responseText}`);
}

const result: unknown = JSON.parse(responseText);
console.log(JSON.stringify({ status: response.status, result }));
```

That byte array is a shape example, not an audio sample. A real test must use a valid fixture. The value of the experiment is controlled comparison: replace only the file, then only the framework path, then only the parser configuration. If a direct route succeeds and the Express or Next.js route fails, inspect middleware ordering and stream consumption. A request body read once is not automatically available to a later multipart parser.

The signal I want from a failed run is precise. A missing boundary implicates serialization or header mutation. A present boundary with no `file` part implicates the field name or append call. A present part with an unexpected filename or MIME type implicates metadata. A correctly parsed part rejected after that point belongs to capability, format, size, or service-contract validation.

One variable.

Here is the failure pattern worth documenting in a review. The browser sends an audio note to a Next.js route, the route forwards it with a new `FormData`, and the forwarding code copies the incoming `Content-Type` header verbatim. The first header may contain a boundary generated for the browser's body; the new body has a different boundary generated by the server-side form object. The receiving parser then looks for delimiters that never occur. A log containing only “400 malformed request” hides the mismatch, while a redacted pair of boundary values, the file field name, and the byte length makes the defect obvious without exposing audio. If the route instead passes the original request stream into a parser, the same symptom can appear after an earlier JSON or logging middleware has consumed that stream. These are separate defects with separate fixes, so the finding should name the layer and the exact observed metadata. I don't change the parser, header, and fixture in one commit; that destroys the comparison.

## What should a code-review finding contain after a 400?

For structured findings, preserve evidence and avoid guessing. A useful record includes a stable rule ID, severity, file and line, the observed request metadata, and one recommended edit. It should also state what was not observed, because “boundary absent” and “boundary mismatch” require different fixes.

| Finding | Evidence to capture | Recommended action |
| --- | --- | --- |
| `missing_boundary` | Header is `multipart/form-data` with no boundary parameter | Let `FormData` and fetch set the header |
| `wrong_field` | Multipart parts exist, but the contract's file field is absent | Use the documented field name |
| `mime_mismatch` | Filename extension and declared media type disagree with the bytes | Derive metadata from the actual input |
| `stream_consumed` | Parser sees an empty body after earlier middleware read it | Put multipart parsing before body consumption |
| `unknown_400` | No sanitized wire metadata or request ID | Add observability before changing application code |

I keep a 400 response as a classification problem, not a retry condition. Retrying the same malformed body three times only creates noise and can make a queue look unhealthy. Retries belong after the request is known to be valid and the failure is transient according to the service contract.

## Limits of this method

This experiment cannot prove transcript quality, language detection, diarization, or production latency. It proves much less—and that is useful. It isolates whether the request reached the service with the intended shape.

The catch is that framework adapters and reverse proxies can impose their own limits, so a locally valid request may still fail at the deployed boundary. A specialist speech service is the better fit when transcription quality or streaming latency is the product's primary risk; a broader runtime may be suitable when reducing credential and integration sprawl matters more. I'm not sure which trade-off wins for an unmeasured workload. Run the same fixture in the real deployment region, record parse success, end-to-end latency, transcript acceptance, and retry behavior, then decide.

Before copying this pattern into an e-commerce review worker, add contract tests that inspect the generated request, a redacted request-metadata log, and a fixture test through the actual Express or Next.js entry point. The decision is not “which client looks easiest?” It is whether every rejected upload can become one correct, reviewable finding.
